Final lane of the Paker library program: the demo app renders the specification's example components against the composed library instances, proving D1–D3 end-to-end, and lands the project's component-exploration surface (the gallery page).

What changed and why. `demo/` holds one view per spec example plus the gallery shell: `CounterView.tsx` is the spec's Counter (two source cells, the V6 computed, the hook-call `Component` whose button copy is the contractual witness); `StoreView.tsx` is the spec's store example (`actions(store(...))` with `incrementCounter`, `WholeStoreComponent` over the whole-store hook, `AtomicStoreComponent` over the counter property hook); `UsersView.tsx` is the spec's RxJS example verbatim — `rxjs(actions(store, factory), pinned-event-factory)` with `FETCH → tap(incrementBy) → switchMap(fetch) → skipOn → forward.RECEIVE_USERS` (skipOn present, inert: OTHER_ACTION never emits in the witness). Forward/skipOn-using factories pin the event map with a return annotation per the 2026-10-15 parent ruling; the non-forwarding action factories infer unpinned, proving that half of the ruling too. The gallery (`App.tsx`) hash-routes /counter /store /users with zero added dependencies; `main.tsx`/`index.html`/`demo/vite.config.ts`/`npm run demo:dev` give humans the live app.

Behavior decisions inside the lane: the atomic component's users read is a non-reactive `data$.get()` while its counter read is the property hook — deliberate, because it lets the D2 test witness S5 scoping observably (a data-only change commits the whole-store component, the atomic one never re-renders and its user display stays stale by design); this is exactly what "atomic subscriptions" means for rendering and matches the parent mockup's copy. The network edge sits behind the single `api.ts` `fetchUsers()` function: tests stub global `fetch` with the two-user witness per testing-guide; the dev server answers /api/users statically from `demo/public/api/users` (same witness) so the live demo runs offline. Spec example instances are module-level (per the SSR consumption rule — created alongside their sources); demo tests reset them through the published `reset()`/`set()` APIs rather than re-creating per render.
